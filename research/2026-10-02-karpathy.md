# 从 Karpathy 的帖子到 Agent 语言与输出标准

研究日期：2026-10-02。本文记录来源、推论及取舍；运行规则以仓库规范为准。文中的“采纳”表示本项目的设计决定，不表示已被实验验证。

## 原帖与可用启发

[Karpathy 原帖](https://x.com/karpathy/status/2105819303471976479) 发布于 2026-10-01 17:37 America/Los_Angeles，即 2026-10-02 00:37 UTC。本次通过 X 浏览器直接读取正文。

作者建议尝试让模型按 ASD-STE100 解释内容，主观感到回答往往更易读；有时只要求接近该标准，以放松严格限制。他随后讨论图解、可交互 HTML 页面，以及按需制作主题讲解视频，特别看好类似 3Blue1Brown 的讲解形式配合语音生成。更大的判断是：模型承担更多执行工作后，人类的工作会更多转向监督与理解，低成本代码可以服务于一次性的解释工具。

有价值的启发是同时改进语言和表达形式，让输出帮助人理解、判断和行动。帖中的可读性感受、媒介偏好和未来判断应分别看待：它们不是对中文 Agent 的受控实验，也没有证明图像、网页或视频存在通用的质量排名。“接近标准”可作为提示尝试，不能当作可以测量的合规比例。

## 延伸原始来源

### ASD-STE100：控制歧义，保持技术含义

[官方 FAQ](https://www.asd-ste100.org/STE_faq.html) 说明 STE 由写作规则与受控词典构成，允许领域技术词；执行前必须知道的条件应放在动作之前。标准针对英语技术文档，强调清楚表达复杂系统，并非把内容变幼稚。

本项目借鉴术语一致、条件明确和含义保真。英语词性、时态、词数和 `-ing` 限制不能直接映射为中文禁令；我们的规范不声称符合 ASD-STE100，也不重新发布其标准正文或词典。

### 开发者写作与 DSL：把约束写成可检查对象

[Google 开发者文档摘要](https://developers.google.com/style/highlights) 强调直接、清楚、面向读者的技术说明。本项目借鉴它组织技术内容，不把英文风格指南逐字套入中文。

[Satoshi 链接的 DSL 设计文章](https://github.com/receptron/mulmoclaude/blob/main/docs/papers/dsl-as-harness.md) 已直接读取。文章主张让模型生成受约束、可校验的中间表示，再交给执行层处理；也讨论过度约束时的退出路径。本项目据此保留稳定字段、可编辑源文件和能力不符时的明确说明。这是作者的工程设计论述；本次未运行项目，也未独立核查其所引用实验，不能接受“格式约束就保证整体正确”这样的外推。

### Plain language：面向实际受众

[Digital.gov 原则](https://digital.gov/guides/plain-language/principles) 要求根据受众知识、经验和需求组织表达，反对把通俗表达等同于统一降低阅读水平。[设计指导](https://digital.gov/guides/plain-language/design) 支持关键内容前置，以及适当的标题、列表和表格。

本项目据此保留必要专业术语，并按任务决定篇幅和结构。这些是政府沟通实践指导；把它们用于中文 Agent 是适配，不是原来源的实验结论，也不适合机械约束所有文学创作。

### 多媒体学习：相关性比形式数量更重要

[Mayer 的多媒体原则](https://www.cambridge.org/core/books/abs/cambridge-handbook-of-multimedia-learning/multimedia-principle/D09A773C7C5C214FA19D4C9841FBC83B) 讨论相关文字和图像对教学的价值；[连贯性原则](https://www.cambridge.org/core/books/abs/multimedia-learning/coherence-principle/4E80B70CB76E2166B76E5653EBDE7D3E) 支持排除无关的文字、图片和声音；[分段原则](https://www.cambridge.org/core/books/abs/multimedia-learning/segmenting-principle/37240877DDA0362355ADB39936027982) 讨论允许学习者按节奏推进的材料，尤其适用于复杂、快速、读者不熟悉的讲解。

这些证据来自教学与学习迁移研究，不能推导出所有回答应升级成视频。本项目对表格、图解、交互和动态演示的选择规则属于设计推论，需要用实际任务检验。

### W3C：让信息能够被不同方式访问

[复杂图像指导](https://www.w3.org/WAI/tutorials/images/complex/) 要求文字替代能够传达图像中的重要信息，建议正文说明主要关系或趋势。[音视频规划指导](https://www.w3.org/WAI/media/av/planning/) 区分媒介类型、用户需要和不同合规等级下的字幕、文字稿及视觉描述。

本项目保留必要文字替代和播放控制，不把字幕当作可删除的“冗余”。具体 WCAG 要求因内容和等级而异；提供几个替代文本不能据此宣称全面合规。[清晰内容指导](https://www.w3.org/WAI/WCAG2/supplemental/objectives/o3-clear-content/) 属于补充认知无障碍指导，并非满足 WCAG 的必选清单。

### 检验理解，而不只检验句式

[Digital.gov 理解测试](https://digital.gov/guides/plain-language/test/) 与[复述测试](https://digital.gov/guides/plain-language/test/paraphrase-testing) 建议观察读者如何解释内容、找到信息和完成任务。读者回答“我看懂了”不足以证明理解正确。

本项目把这些思路用于长期复用的规范和重要模板：保留容易误解的样例，检查信息保真和任务完成。无需为每条聊天组织正式用户研究；Agent 自检、另一模型打分或 linter 通过也不等于真实读者测试。

## 采纳、调整与不采纳

| 决策 | 内容 | 原因 |
| --- | --- | --- |
| 采纳 | 稳定关键术语；明确主体、动作、条件和例外。 | 降低歧义，同时保留原始含义。 |
| 采纳 | 先给任务所需的答案，再提供相称的证据和细节。 | 方便定位信息，不把简短当作唯一目标。 |
| 采纳 | 每个图表、交互或视频都应解决具体理解或操作问题。 | 媒介服务内容；用户指定的交付形式优先。 |
| 采纳 | 图像和动态内容保留必要文字替代；说明验证范围。 | 便于访问、复用和检查。 |
| 调整 | 将 STE 的清晰原则适配到中文。 | 保留受控表达的价值，不机械复制英语语法约束。 |
| 调整 | 将“更好的媒介”改为“更适合当前任务的媒介”。 | 表格、图解、交互和视频不是单向升级阶梯。 |
| 调整 | linter 只提示可检查的形式问题，另用样例复核含义。 | 指标改善不能证明事实、逻辑或读者理解正确。 |
| 不采纳 | 固定百分比的 STE 合规、中文硬性句长、全面禁用词表。 | 缺乏可操作定义，易伤害准确性和自然表达。 |
| 不采纳 | 默认生成 HTML、动画或视频；把装饰当作解释增益。 | 增加制作、阅读和维护负担，收益取决于任务。 |
| 不采纳 | 把作者感受、评论热度或演示存在当作效果证明。 | 三者均不能替代正确性与使用效果验证。 |

## 研究限制与后续维护

- 用户已澄清“下面的分享”指原帖评论；本版按此范围研究，没有假设另有未提供材料。
- 评论覆盖有限，不代表完整讨论。视频存在不代表内容正确，社区实现存在不代表有效。
- 延伸研究核实了官方页面和作者的章节摘要，未将无法访问的全文当作已读；不外推为对中文 Agent 的直接实验支持。
- 本版提供可执行的设计起点，尚未完成真实用户理解测试。后续应按实际误解修订规则，并保留版本、案例、来源和例外，避免规则只增不减。
