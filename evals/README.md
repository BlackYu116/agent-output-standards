# 语言与输出规范评估

这些用例检查规范是否帮助 Agent 保留原意、解释清楚并交付合适的输出。它们是可扩充的回归样本，不代表所有写作场景。

## 怎么运行

1. 选择要评估的规范或 skill 版本，记录模型、版本、运行日期和可用工具条件。
2. 向执行 Agent 提供该规范或 skill，以及单个用例的 `prompt` 和可选 `source_text`。**不要提供 `expected`、`failure_modes` 或本评估说明。** 每个用例在独立上下文中运行，避免答案相互泄漏。
3. 保存原始输出。评审者再结合完整用例检查结果，先看事实与语义，再看清晰程度和格式。不要要求逐字匹配参考要点。
4. 记录“通过”“需修改”或“无法判断”，附具体输出片段及原因。未知事实、工具状态或语义保真不合格时，不能用文风优点抵消。

这里不调用模型 API，也不附自动执行脚本。可以人工运行，或接入已有评估系统；任何自动评审都应保留人工复核入口。

## 看什么

**语义保真优先。** 检查条件、否定、范围、数字、时间、不确定性和义务强度；“必须”不能被润色成“建议”。同时检查有没有增添来源不支持的事实、因果或已完成状态。

其次检查输出是否服务于具体读者和任务：简单事实直接回答；明确要求 HTML 时交付 HTML；术语需要解释，但中文不必机械地切成短句；创作中有意的重复和迟疑可以保留。不是每篇回答都需要相同标题、长度或版式。

**真实读者能否理解和正确使用，是最终检验。** 对解释类输出，请目标读者用自己的话复述关键关系，或完成一个相关的小任务。记录误解发生在哪里，再修规则与示例。不要把 linter 通过率、禁词命中率、句长或模型评分称为“理解率”。

## 怎么维护

对照当前版本与修改后的版本，在相同任务与工具条件下比较。出现波动时保留多个独立样本，避免凭一次输出认定改进；不设置缺乏依据的通用分数或精确权重。

每次真实使用发现问题，优先补充一个去除隐私信息的具体用例，并写清预期与失败模式。避免只收集支持新规则的样例：例如“简单事实不需要 HTML”和“用户指定 HTML 应遵守”应一起保留。语义允许的不同表达都应接受。
